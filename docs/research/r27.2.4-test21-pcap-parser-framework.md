# R27.2.4 — Canonical Test 21 PCAP parser framework

## Scope

R27.2.4 is the first implementation phase selected by the post-R27.2.2 residual-family triage. It covers exactly two host-only historical Test 21 parsers:

- `scripts/tests/parse_test21_r3_3_3_pcap.py`
- `scripts/tests/parse_test21_r3_3_3_1_pcap.py`

Both files are untracked historical research in the accepted repository snapshot. Their exact identities remain locked at:

```text
r3.3.3   3ea78c9268db98588f85676d6e9375dbafb95478285e464f31d16f6d09815608
r3.3.3.1 a39cf96ee91edd737b2f626f6201ad88379f2ca279ece101fec9216a7d271f04
```

R27.2.4 does **not** modify, delete, or shim either historical parser. They remain the behavioral oracle for this stage.

## Canonical interface

```bash
scripts/rokid-research network parse-pcap --list

scripts/rokid-research network parse-pcap \
  --revision r3.3.3.1 \
  --pcap /path/to/capture.pcap \
  --uid-map /path/to/uid-map.json \
  --output /path/to/private-output \
  --sslkeylog /path/to/sslkeylog.txt
```

The canonical parser is implemented by `scripts/research/canonical/pcap_parser.py`; revision differences are data in `profiles/test21-pcap-parsers.json`.

## Shared parsing core

The canonical implementation consolidates the common architecture:

- classic PCAP endian/time-resolution handling;
- PCAPdroid trailer recovery;
- IPv4/IPv6 and TCP/UDP extraction;
- DNS query recovery;
- TLS ClientHello/SNI inspection;
- cleartext HTTP request metadata extraction;
- path identifier/query sanitization;
- five-tuple-equivalent flow-key generation;
- optional tshark TLS-keylog metadata extraction; and
- private JSONL/JSON result generation.

The r3.3.3.1 profile retains its later semantics explicitly:

- PCAP linktype-aware raw-IP parsing;
- frame numbers;
- public-endpoint classification;
- target-package-only attribution maps;
- frame-trailer-before-flow-tuple HTTP attribution; and
- expanded summary/output markers.

## Equivalence boundary

The R27.2.4 verifier compares each historical parser with the canonical revision profile on synthetic fixtures. The positive matrix covers:

1. Ethernet PCAP with PCAPdroid trailers and a fake deterministic tshark result;
2. short/truncated PCAP input that returns a valid zero-row summary; and
3. for r3.3.3.1, raw-IP PCAP linktype 101.

For successful cases the gate requires:

- zero return codes;
- byte-identical stdout;
- byte-identical `network-packets-private.jsonl`;
- byte-identical `decrypted-http-private.jsonl`; and
- byte-identical `network-parse-private.json`.

The negative matrix also requires both implementations to reject unsupported PCAP magic with a nonzero result and the same `unsupported PCAP magic` semantic error.

The synthetic tshark executable is local to the verifier. It performs no network operation.

## Safety and lifecycle

R27.2.4 is equivalence-only:

```text
historical parser action: NONE
repository deletion: NONE
device operation: NONE
privileged operation: NONE
network operation: NONE
```

If the real-repository run passes 2/2 profile equivalence with both historical source locks intact, a later phase may archive the two original parser implementations and replace their historical paths with compatibility shims. That reduction is intentionally not performed here.

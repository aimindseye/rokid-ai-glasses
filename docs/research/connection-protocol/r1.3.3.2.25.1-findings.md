# r1.3.3.2.25.1 Findings — Stock Session Establishment

## Scope and evidence

This release analyzes the accepted stock-only pairing/reconnect capture whose
private-evidence SHA-256 is:

```text
5a36349d3e18f8896fa8e6da728d4ad684852738b860d44156d53824b155df42
```

No Developer Mode toggle occurred. Developer Mode request attribution is
therefore not part of this result.

## Closed establishment sequence

The accepted capture establishes this sequence:

1. Hi Rokid opens a BLE GATT connection to the glasses.
2. After MTU negotiation, Hi Rokid reads characteristic
   `00009301-0000-1000-8000-00805f9b34fb`.
3. The characteristic value supplies a runtime RFCOMM service UUID, the Classic
   Bluetooth address, opaque account/session material, and a glasses-type field.
4. Hi Rokid closes its BLE GATT client and requests an RFCOMM socket using the
   runtime-provisioned UUID.
5. SDP resolves that UUID to server channel **3**.
6. L2CAP establishes the RFCOMM bearer with phone-local CID `0x007f` and
   glasses-remote CID `0x0044`.
7. The RFCOMM multiplexer completes SABM/UA and the data-link channel completes
   on **DLCI 6** with MTU **990**.
8. The socket opens; 30 ms later CXR reports `BLUETOOTH_AVAILABLE`; the first
   CXR request follows 1 ms later.

The runtime UUID and account material are intentionally omitted from public
files. Their SHA-256 identities are retained in the machine-readable
publication.

## Fixed UUID behavior

Before runtime provisioning succeeds, the app repeatedly tries a fixed cached
UUID. In this capture:

- nine CXR-level connect calls are visible;
- Android receives 18 RFCOMM socket attempts;
- all 18 corresponding SDP resolutions return failure with server channel 0.

The fixed UUID is therefore a cached, fallback, or pre-provisioning candidate;
it is not the active stock data channel in this run.

## Engineering consequence

The next client must not hard-code one of the cached SDP UUIDs as the stock CXR
socket. It must first reproduce the read-only BLE connection-information step,
obtain the current runtime UUID and associated opaque material, then open
RFCOMM SCN 3/DLCI 6 without transmitting application payloads until the
authentication and framing contracts are independently closed.

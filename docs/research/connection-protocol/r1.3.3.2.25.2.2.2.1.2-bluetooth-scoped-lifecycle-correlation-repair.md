# r1.3.3.2.25.2.2.2.1.2 — Bluetooth-scoped lifecycle correlation repair

## Purpose

This additive repair reanalyzes the existing r25.2.2.2 private evidence archive
offline. It corrects the remaining defects in r1.3.3.2.25.2.2.2.1.1:
Bluetooth-unscoped field extraction, split lifecycle attempts, reversed UID/PID
interpretation, incomplete cross-source deduplication, close-event
misclassification, conflated UUID domains, and missing zero-payload source
retention.

## Accepted lifecycle model

A candidate begins at a Bluetooth socket request and is coalesced through native
RFCOMM creation, open, client-connect, cleanup, and explicit transport close.
Temporal gaps alone never split the attempt. A later incompatible root request
starts another attempt.

The mandatory regression lifecycle is bounded from `2026-07-27T14:00:11.506Z`
through `2026-07-27T14:00:17.645Z`. It contains:

- requested service UUID `89679c22-9cac-464d-86d8-d254bc8b649b`;
- Android requestor UID/PID `10320/23810`;
- slot `45`, port handle `29`, SCN `3`, DLCI `6`, and MTU `990`;
- `is_server=false` and `on_cli_rfc_connect` client semantics;
- an ordered native open and explicit close;
- retained zero-payload counters or an explicit zero-payload assertion, with no
  positive counter or payload-data event.

The 128-bit requested UUID and native service-class UUID such as `0x1101` are
separate evidence domains and are not treated as contradictory.

## Evidence controls

- Only Bluetooth/RFCOMM-scoped records may contribute tuple fields.
- `from uid/pid=UID/PID` is parsed as an ordered pair.
- Android log-prefix UID/PID values are used only in scoped socket records.
- Endpoint values must match Bluetooth-address syntax.
- Explicit `RFC_PORT_EVENT_CLOSE` text overrides function-name text such as
  `rfc_port_sm_opened`.
- Canonical deduplication removes timestamp, UID/PID/TID, priority, and tag
  wrappers while preserving all source references.
- The exact metadata interval is enforced before correlation.
- Slot cleanup is corroborating state but is not accepted as the required
  transport close by itself.
- Zero payload cannot be inferred from silence. Retained counters or an explicit
  zero assertion are mandatory, and positive counters or payload events fail the
  gate.
- Exactly one fully qualifying attempt is required for promotion.

## Scope limitation

A PASS applies only to the locked source archive and captured interval. It does
not establish application payload semantics, behavior outside the attempt, or
stock-client equivalence beyond the observed RFCOMM lifecycle.

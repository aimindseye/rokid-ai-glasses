# r1.3.3.2.25.2.3.1 — Pixel/AOSP HCI Snoop Preflight Repair

## Purpose

Repair the r25.2.3 false-negative preflight on Pixel and current AOSP-derived Android builds. The rejected preflight relied on legacy `settings secure bluetooth_hci_log` and legacy persistent properties. Current Android can instead expose the configured mode through `settings global bluetooth_btsnoop_default_mode`, the active/default properties, or Bluetooth service dump state.

## Readiness states

- `CONFIRMED_FULL`: active service/property state is full.
- `CONFIRMED_FULL_CONFIGURED`: the current global/default configuration is full.
- `CONFIRMED_FULL_LEGACY`: only a legacy control proves full.
- `PROVISIONAL_UNKNOWN`: controls are hidden or unset; capture proceeds, but the bugreport must contain a parseable HCI snoop stream.
- `CONFIRMED_FILTERED`: rejected because filtered HCI cannot prove absence of application payload.
- `CONFIRMED_DISABLED`: rejected before capture.
- `RESTART_REQUIRED`: configuration is full but active Bluetooth state is explicitly disabled.

## Proof authority

Preflight is only a readiness hint. The post-bugreport binary btsnoop census remains authoritative. Full zero-payload promotion still requires a complete, lossless, temporally correlated RFCOMM DLCI lifecycle and zero non-control UIH information bytes in both directions.

## Device mutation policy

The scripts do not change settings, set properties, restart Bluetooth, reboot, request root, or contact the glasses directly outside the user-triggered connection attempt.

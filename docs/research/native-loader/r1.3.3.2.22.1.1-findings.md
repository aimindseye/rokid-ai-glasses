## Main conclusion

The global Hi Rokid Android package uses a protected native-loader path that
cannot be reconstructed completely through ordinary static APK inspection.
Runtime evidence establishes that the loader materializes a secondary runtime
image, resolves relocations, executes initializer callbacks, dynamically
registers JNI methods, returns a protected class-loader boundary and proceeds
into protected Java application loading.

The strongest observed flow is:

```text
libnesec.so
  → secondary mapping captured
  → 68 external relocation slots captured
  → post-transform bytes captured by hash
  → 29 initializer callbacks executed
  → 11 MyJni methods registered for the exact class
  → MyJni.cl entered and returned
  → MyJni.load entered
  → MyApplication loaded twice
  → Application.attach entered
```

## RegisterNatives class attribution

The 14 methods are distributed as follows:

| Class | Method count |

| `android.net.TrafficStats` | 2 |
| `com.netease.nis.wrapper.MyJni` | 11 |
| `dalvik.system.DexFile` | 1 |

The earlier aggregate wording “14 MyJni methods” was too broad. Exact runtime
class attribution supports **11** methods for `MyJni`.

## Native execution evidence

- `MyJni.cl` — entry and return observed; elapsed time 741 ms.
- `MyJni.load` — entry observed; return not observed before process exit.

The process ended with Android `EXIT_SELF`, status 28, without a tombstone, and
the application later relaunched. The evidence does not establish why the
process chose that exit status.

## Java handoff evidence

Observed Java events include:

- Java bridge ready;
- nine lifecycle/class-loader hook overloads installed;
- two `ClassLoader.loadClass` events for
  `com.netease.nis.wrapper.MyApplication`;
- one `Application.attach` entry event.

Not observed:

- `Application.attach` return;
- `LoadedApk.makeApplication` execution;
- `Instrumentation.callApplicationOnCreate` execution;
- full protected application class inventory.

## Controller-recovery finding

The original active controller emitted a false component failure after a
second idempotent RegisterNatives hook-discovery pass installed zero **new**
hooks even though two valid hooks already existed. The corrected interpretation
is:

```text
TOTAL_HOOK_COUNT > 0 and NEW_HOOKS_THIS_PASS == 0
  → ALREADY_READY
  → not a component failure
```

The later `script has been destroyed` exception was a secondary controller
exception after the target process had already exited. The recovered closure
preserves the 102-event partial stream instead of discarding it.

## Implication for future work

The native-loader and Java-handoff architecture is closed sufficiently to move
forward. The next research phase should recover protected DEX/class
materialization and map the 11 MyJni methods to Java callers and user-visible
features. It should not continue widening the loader investigation without a
specific unresolved boundary.
